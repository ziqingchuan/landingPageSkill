# 落地页基础业务规则

## 1. 文档职责

本文档只定义落地页必须遵守的业务约束、数据语义和交互结果，确保页面功能与 `user_config_info.json` 一致。

本文档不定义页面编排或设计，不规定：

- 页面必须有哪些营销模块；
- Hero、价值点、流程、FAQ、案例等模块是否出现；
- 模块数量、顺序、篇幅或叙事结构；
- CTA 出现次数、放置位置或视觉形式；
- 表单采用整页、分步、弹层、抽屉还是其他表现；
- 栅格、排版、色彩、组件样式和动效。

AI 应根据实际配置、用户补充要求、内容密度、目标受众和创意方向，自主决定信息架构、内容取舍、模块组合与顺序。不得把本文档转化为固定页面模板。

## 2. 文档边界

| 信息来源 | 负责内容 |
| --- | --- |
| `user_config_info.json` | 当前项目的真实配置，决定有哪些科目、字段、问题和功能开关 |
| `user-config-spec.md` | 字段说明书，用于理解字段含义、类型和允许值 |
| `business-rules.md` | 业务不变量、功能开关语义、校验和结果状态 |
| `frontend-design.md` | 视觉方向、可用性、响应式、可访问性和界面质量 |
| AI 的页面方案 | 信息架构、内容重点、模块选择、模块顺序、叙事节奏和具体表现 |

发生冲突时按以下顺序处理：**有效配置 → 业务规则 → 用户明确要求 → frontend-design 审美方向**。AI 在这些边界内自主编排，不能改变配置事实和业务结果。

## 3. 配置解释原则

1. AI 把传入的有效配置视为只读事实，只负责理解和使用；配置的生成、默认值、规范化和校验由用户侧程序负责。
2. 字段说明书中的示例、默认值和解释不是当前项目数据。
3. `enabled=true` 的业务字段必须在对应流程中可被用户填写；`enabled=false` 的字段不得参与显示、校验或提交。
4. 字段的必填性读取 `required`，归属读取 `owner`，不得为了版面完整擅自更改。
5. 功能开关关闭时，不展示或暗示该功能；功能开启时，必须提供可完成的行为，不能只出现装饰性入口。
6. 自由文本要求可以影响内容和表达，但不能覆盖结构化字段或核心功能开关。

## 4. 真实性与内容边界

- 所有事实型内容必须来自配置、用户明确提供的信息或已接入的可信数据源。
- 不得虚构师资、评价、成绩、排名、奖项、价格、优惠、学员数量、合作品牌、资质或预约库存。
- 缺少事实依据时，可以省略相关内容，也可以使用不新增事实的概括性表达。
- 编辑态占位必须明确标注为占位，不能在访客页面伪装成真实内容。
- AI 可以创作文案、比喻、标题和叙事角度，但不得把创意表达包装成未经提供的事实或承诺。

这些限制只约束内容真实性，不要求或禁止任何特定页面模块。

## 5. 转化目标与 CTA 行为

- 页面应有清晰且一致的主要转化目标，其含义必须与配置一致。
- CTA 文案必须描述点击后真实发生的动作，不得把留资写成预约成功，也不得把咨询写成购买完成。
- CTA 必须连接到可操作的下一状态，例如聚焦输入、打开流程、进入下一任务或提交数据。
- 同一最终目标可以使用不同语境的 CTA 文案，但不得产生互相冲突的转化承诺。
- CTA 的数量、位置、形式和分布由 AI 根据页面方案自主决定。

## 6. 字段与联系方式

### 6.1 字段通用规则

- 只收集配置中启用且当前科目适用的字段。
- 隐藏或当前不适用的字段不得被校验或提交。
- 错误信息应能定位到具体字段或具体业务条件。
- 用户返回、切换分支或修正错误时，应保留仍然有效的输入。
- `owner=parent` 的数据可在不同孩子、不同科目间复用；`owner=child` 的数据必须归属于具体孩子。

### 6.2 进线科目 vs 拓科科目

`fields` 数组描述的是**进线科目**（`project.subject`）的字段配置。当用户在追加流程中选择**拓科科目**（`extraSubjects` 中的科目）时，字段适用性按以下规则重新判断：

**通用字段（所有科目均适用）：**

| 字段 | 说明 |
| --- | --- |
| `childName` | 孩子称呼，所有科目都需要 |
| `phone` | 家长手机号，取决于 `contactMode` |
| `email` | 家长邮箱，取决于 `contactMode` |
| `region` | 时区/国家，所有科目必须启用、必填、锁定 |
| `commLang` | 沟通语言，所有科目适用 |

**科目条件字段（仅特定科目适用）：**

| 字段 | 中文 | 数学 | 英文 |
| --- | --- | --- | --- |
| `age` | 必须启用、必填、锁定 | 不强制（可配置启用） | 不强制（可配置启用） |
| `level`（中文水平） | 必须启用、必填、锁定 | 不适用 | 不适用 |
| `grade`（年级） | 不强制（可配置启用） | 必须启用、必填、锁定 | 必须启用、必填、锁定 |

规则：

- 切换到拓科科目时，**科目条件字段**按新科目的硬规则重新判断是否启用、是否必填。
- 配置中 `fields` 数组的 `enabled` / `required` / `locked` 是进线科目的状态；拓科科目不以 `fields` 数组为准，而以上表的科目硬规则为准。
- 通用字段（`childName`、`phone`、`email`、`region`、`commLang`）在所有科目中均保持配置中的启用/必填状态。
- 不适用的科目条件字段不展示、不校验、不提交（例如选数学时不出现 `level`，选中文时 `grade` 按配置决定是否出现）。
- 科目条件字段的 `owner` 均为 `child`，归属于具体孩子。

### 6.3 联系方式模式

| `contactMode` | 业务含义 |
| --- | --- |
| `phone` | 使用手机号完成联系方式收集 |
| `email` | 使用邮箱完成联系方式收集 |
| `either` | 用户在手机号和邮箱中任选一种，当前选择的方式必须有效 |

- `either` 不得被解释为手机号和邮箱同时必填。
- 切换联系方式时保留用户已经输入的内容，但只校验当前使用的方式。
- 验证码是单一流程能力，与当前实际使用的进线字段一对一绑定；不分别配置手机号验证码和邮箱验证码。
- `contactMode=phone` 时验证手机号，`contactMode=email` 时验证邮箱，`contactMode=either` 时验证用户实际选择的联系方式。
- 验证码所在流程阶段读取 `verificationStage`；页面中的验证码容器使用 `data-verification-stage` 属性标记该阶段。
- 联系方式的控件形式和在页面中的呈现方式由 AI 自主决定。

## 7. 转化模式

### 7.1 前置需求单元

"前置需求单元"包括：

1. 当前科目下 `enabled=true` 且 `stage=lead` 的字段（科目条件字段按 6.2 节判断是否适用），按 `fields` 数组顺序排列；
2. 当前科目需要展示的 `leadQuestions`（仅当前科目的题目），按 `sortOrder` 排列。

默认交互是一页只处理一个前置需求单元：

- 当前单元校验通过后才能进入下一单元；
- 用户可以返回上一单元修改答案；
- 前进、后退或发生校验错误时保留已有有效答案；
- 进度只反映实际参与当前流程的单元，不把联系方式、预约或结果页混入问题进度；
- "一页一题"是流程基线，不要求使用弹窗，也不限制页面采用整页、抽屉或其他视觉容器。

### 7.2 `flowMode=direct`

- 不展示或校验 `leadQuestions`，但配置中的问题保持不变。
- 用户触发主 CTA 后直接进入联系方式页面，不先展示前置需求单元。
- 尚未收集的启用字段在联系方式完成后进入资料补充阶段；不得因为跳过前置问题而丢失必填字段。

### 7.3 `flowMode=lead_first`

- 用户触发主 CTA 后，先按 7.1 逐页完成所有前置需求单元，再进入联系方式页面。
- 没有有效前置需求单元时自动跳过该阶段，行为等同于直接进入联系方式页面；不得展示空问题页。
- `leadQuestions` 的必答状态读取 `required`，字段必填状态读取字段自身的 `required`（按当前科目适用规则）。

### 7.4 联系方式之后

- 联系方式页面负责当前 `contactMode` 对应的联系方式和隐私同意。
- 验证码功能出现在 `verificationStage` 指定的阶段，并验证当前实际使用的进线字段；验证成功后才能离开该阶段。
- `verificationStage=lead` 仅在 `flowMode=lead_first` 时有效；`verificationStage=booking` 仅在 `booking=true` 时有效。
- 联系方式完成后，依次进入剩余资料补充、约课（仅 `booking=true`）、最终提交和结果页；验证码节点按其配置阶段插入对应流程。
- `booking=false` 时跳过预约，完成剩余必填资料后直接提交。

以上顺序是产品默认状态机。AI 可以设计各状态的文案、视觉和容器，但不能合并掉"一页一题"、把真实约课提前到联系方式之前，或绕过验证与必填资料。

## 8. 预约规则

学习时间偏好、通常空闲时段等需求问题只用于了解意向，不等同于真实预约。只有基于真实日期、时段或可提交预约信息的阶段才属于本节的约课流程。

### 8.1 `booking=false`

- 不收集日期、时间、课时或预约库存。
- 不显示预约摘要、日历同步或"预约成功"等结果。
- 提交结果只能表达信息已提交、需求已收到或与实际动作一致的状态。

### 8.2 `booking=true`

- 真实预约阶段在联系方式和资料补充完成后开始。
- 用户必须能够提供或选择完成预约所需的信息（日期、时段），并在确认前检查和修改。
- 成功结果必须基于真实提交结果，不得用静态界面伪造成功。
- 没有真实时段数据时，不得虚构可预约库存；原型数据必须明确标注。
- `syncCalendar=true` 时，日历同步只能在预约成功后提供。
- 每个"孩子 + 科目"组合独立预约，不共享预约时段。

预约信息在页面中的位置、交互容器和步骤拆分由 AI 自主决定。

## 9. 多娃与多科循环（购票式流程）

多娃多科采用**购票式流程**：像买火车票一样，先选目的地（科目），再选乘客（孩子），然后完成购票（预约/报名）。每次只完成一个"孩子 + 科目"组合的提交。所有组合的状态集中在结果页展示。

### 9.1 结果页（总览页）

结果页是整个流程的**总览页**，展示所有可能的"孩子 + 科目"组合及其状态，而不仅仅是刚刚完成的那个。

**展示内容：**

- 顶部祝贺信息：说明本次完成的动作（如"成功领取体验课"或"预约成功"）。
- **组合总览**：以"孩子 + 科目"为单位，列出所有组合的状态。
  - 总组合数 = 孩子数 × 科目数（`project.subject` + `extraSubjects`）。
  - 每个组合显示：科目名称、孩子称呼、当前状态（未开始 / 进行中 / 已完成 / 已预约）。
  - 已完成的组合可以点击查看详情（预约时间、提交信息等）。
  - 未完成的组合不展示详细信息。
- 下方可放置后续服务入口（如学习规划师二维码），没有真实数据时不得生成虚假内容。

**只有一个操作按钮：**

- `booking=true` 时按钮文案：**"继续约课"**
- `booking=false` 时按钮文案：**"继续报名"**
- 点击后进入"选择科目"步骤。
- 当所有组合均已完成时，按钮变为不可用或文案变为"全部完成"，明确告知用户当前流程已结束。

### 9.2 第一步：选择科目

点击"继续约课/继续报名"后，首先进入**科目选择页**。

- 展示所有可用科目：`project.subject`（进线科目）+ `extraSubjects`（拓科科目）。
- 每个科目以卡片形式呈现，包含科目名称、适用年级/年龄范围、简短亮点。
- 科目卡片上显示该科目的完成进度：有几个孩子已完成 / 共几个孩子。
- 如果某个科目下所有孩子都已完成，该科目的按钮置灰并标注"全部已预约"或类似文案，不可重复选择。
- `multiSubject=false` 时，只展示 `project.subject`，不出现其他科目。
- 用户选择一个科目后，进入"选择/添加孩子"步骤。
- 提供返回结果页的入口。

### 9.3 第二步：选择或添加孩子

选定科目后，进入**孩子选择页**。此页面的行为类似于火车票的乘客选择：

**已有孩子列表：**

- 列出所有已添加过的孩子。
- 每个孩子项显示：孩子称呼、对当前科目的状态（未开始 / 已完成）。
- 已完成该科目的孩子显示"已预约"或"已报名"标记，不可重复选择。
- 未完成该科目的孩子可以点击选中；选中后显示选中状态（如勾选标记）。
- 同一时刻只能选择一个孩子进行本次预约/报名。

**添加新孩子：**

- `multiChild=true` 且当前孩子总数 < `maxChildren` 时，提供"添加新孩子"入口。
- `multiChild=false` 时不提供添加新孩子入口。
- 添加新孩子时，在内联输入框中填写孩子称呼即可初步添加；详细资料在后续步骤中补充。
- 孩子总数达到 `maxChildren` 上限时，隐藏添加入口。
- 如果输入的孩子称呼与已有孩子重复，提示"该学员已存在，请添加另一个孩子称呼"，不允许重复创建。

**选中状态：**

- 选中一个孩子（已有或新添加）后，页面底部显示当前操作摘要，如"当前正在为 [孩子称呼] 预约 [科目名称] 试听课"。
- 提供"重新选择科目"的返回入口。
- 点击"下一步"后，进入该孩子 + 该科目的资料与预约流程。

### 9.4 第三步：资料补充与预约/报名

进入具体的"孩子 + 科目"组合流程后，按以下顺序完成：

1. **资料补充**：
   - 收集该科目适用的、尚未填写的必填字段（按 6.2 节科目条件字段规则）。
   - `owner=parent` 的数据（联系方式、地区、沟通语言）如果已存在则直接复用并允许修改。
   - `owner=child` 的数据（孩子称呼、年龄、水平、年级等）如果该孩子已有则直接复用并允许修改；没有则需要填写。
   - 科目条件字段按新科目判断适用性（例如选数学时出现 `grade`，不出现 `level`）。
   - 如果该科目下该孩子的所有必填字段已有数据，可跳过资料补充直接进入预约/提交。

2. **前置需求单元**（仅 `flowMode=lead_first` 且当前科目有有效前置单元时）：
   - 按 7.1 逐页完成当前科目的前置需求单元。
   - 如果该孩子该科目已答过前置问题且数据有效，不重复提问。

3. **验证码**（仅 `verificationStage` 对应阶段且尚未验证时）：
   - 家长联系方式已验证且仍有效时，不重复验证。
   - 验证当前实际使用的进线字段（手机号或邮箱）。

4. **预约**（仅 `booking=true` 时）：
   - 选择日期和时段，完成真实预约。
   - 预约确认前允许返回修改。

5. **提交与返回**：
   - 提交成功后自动返回结果页。
   - 结果页更新该组合的状态为"已完成"或"已预约"。
   - 重新计算剩余可用组合，更新"继续约课/继续报名"按钮的可用状态。

### 9.5 数据复用规则

- **家长级数据（`owner=parent`）**：联系方式、地区、沟通语言等，在所有孩子、所有科目间共享；只在第一次时收集，后续循环自动复用，并允许用户主动修改。
- **孩子级通用数据（`owner=child` 且通用）**：孩子称呼，在不同科目间共享；换科目时不重新收集。
- **孩子级科目条件数据（`owner=child` 且科目条件）**：年龄、水平、年级等，按科目判断适用性；同一孩子在不同科目中可能有不同的必填字段，但数据本身归属于孩子，跨科目复用（如年龄填过一次，所有科目都能用）。
- **预约数据**：每个"孩子 + 科目"组合独立，不共享。
- **前置问题答案**：按科目区分，同一孩子同一科目不重复提问。

### 9.6 流程示意

```
结果页（所有组合总览）
  │
  └─ 点击"继续约课"
       │
       ├─ 选择科目（科目卡片列表 + 完成进度）
       │    │
       │    └─ 选中某科目
       │         │
       │         └─ 选择/添加孩子（孩子列表 + 添加入口 + 选中状态）
       │              │
       │              └─ 选中某孩子
       │                   │
       │                   └─ 资料补充 → 前置需求(可选) → 验证(可选) → 预约(可选) → 提交
       │                        │
       │                        └─ 成功后返回结果页（更新该组合状态）
       │
       └─ 全部完成 → 按钮置灰，流程结束
```

AI 可以设计各页面的视觉形式、卡片样式、交互容器和动效，但不能改变上述流程顺序，不能在首次提交前展示结果页，也不能在一次提交中混合多个"孩子 + 科目"组合。

## 10. 隐私、提交与状态

- 最终提交前必须获得明确的隐私同意，且默认不勾选。
- 提交中应防止重复提交，并提供可感知反馈。
- 校验失败时，不得提交无效数据；应说明具体问题。
- 提交失败时保留用户输入，并允许安全重试。
- 成功状态必须准确说明本次完成的业务动作和"孩子 + 科目"组合。
- 隐藏字段、未启用功能和未选择分支的数据不得意外进入提交结果。
- 结果页展示所有组合的状态总览，不仅限于刚刚完成的那个。

页面如何呈现这些状态由 AI 结合 `frontend-design.md` 决定，本规则只要求状态真实、可理解且可恢复。

## 11. 管理端发布锁定

- `status=published` 表示落地页正在对外提供服务，管理端必须禁止编辑配置、修改代码和发起 AI 重新生成。
- 已上架项目的编辑入口必须禁用，并明确提示"请先下架后编辑"。
- 不能只依赖入口按钮；直接访问编辑器地址时也必须根据项目真实状态阻止编辑。
- 用户执行下架后，状态变为 `offline`，此时才恢复编辑、保存和重新生成能力。
- 上架、下架和编辑锁定属于管理端生命周期规则，不改变访客落地页的转化状态机。

## 12. AI 自主编排原则

在满足上述业务不变量后，AI 应主动创造与当前项目相匹配的页面方案：

- 自主判断需要哪些内容模块，也可以不使用常见模块；
- 自主决定内容顺序、长短、节奏和视觉叙事；
- 自主决定转化控件嵌入内容、独立呈现或按任务渐进展开；
- 根据科目、主题、投放场景和用户要求形成差异化结构；
- 避免重复套用固定的 Hero、三卖点、三步骤、FAQ、底部 CTA 模板；
- 不为满足文档而凑模块、凑卡片、凑步骤或重复 CTA。

业务正确性通过行为和结果验收，不通过页面是否长得像某个模板验收。

## 13. 业务验收清单

- 页面使用的字段、问题、科目和功能均能追溯到实际配置。
- 必填、可选、隐藏、验证和数据归属符合配置与科目条件规则。
- `contactMode`、`flowMode`、`booking`、`multiChild`、`multiSubject` 的行为结果正确。
- 前置需求单元逐页完成；没有有效单元时直接进入联系方式，不出现空步骤。
- 每次只提交一个"孩子 + 科目"组合；购票式流程顺序正确（选科目 → 选孩子 → 完成预约/报名）。
- 结果页展示所有"孩子 + 科目"组合的状态总览，且只有一个操作按钮（继续约课/继续报名）。
- 科目选择页显示每个科目的完成进度；全部完成的科目置灰不可选。
- 孩子选择页支持选择已有孩子和添加新孩子；不允许重名；已完成该科目的孩子不可重复选。
- 拓科科目的字段按科目条件规则重新判断（如数学/英文必须有 `grade`，中文必须有 `level`）。
- 家长级、孩子级和科目条件数据在后续循环中按规则复用，没有重复索取或跨孩子串用。
- CTA 与实际下一动作一致，不存在无反馈或虚假承诺。
- 隐私同意、校验、提交中、成功、失败和重试状态真实可用。
- 页面未虚构事实、承诺或库存。
- 已上架项目无法从列表或直接地址进入可编辑状态；下架后恢复编辑。
- 页面结构没有因为本规则被限制为固定模块、固定顺序或固定步骤数量。
