# 工程实现约定

## 1. 文档职责

本文档定义落地页生成时的工程实现层约束，确保生成的单文件 HTML 在目标语言、运行环境和目标终端下保持稳定。这些约束与技术栈、CSS、JS 实现强相关，与业务语义无关。

本文档不定义：

- 业务字段、必填规则、数据归属和转化状态机（见 `business-rules.md`）；
- 视觉方向、字体选择、配色和布局概念（见 `frontend-design.md`）；
- 字段语义和配置结构（见 `user-config-spec.md`）；
- 页面模块、信息架构和叙事结构（由 AI 自主编排）。

本文档的规则是**代码质量护栏**：它们约束"用什么 CSS 单位、怎么命名属性、怎么隔离作用域、怎么验证稳定性"，不约束业务行为是否正确。业务正确性由 `business-rules.md` 保证，本文件不重复其内容。

## 2. 文档边界与优先级

| 信息来源 | 关注层 |
| --- | --- |
| `business-rules.md` | 业务语义层：做什么，与实现无关 |
| `engineering-conventions.md` | 工程实现层：怎么做才稳定，与语言/环境/浏览器强相关 |
| `frontend-design.md` | 视觉审美层：怎么做才独特 |
| AI 的代码实现 | 具体选择器和变量命名 |

冲突处理：**业务不变量 > 工程约定 > 审美方向**。工程约定不得改变业务结果；当审美方向要求使用某项会触发工程风险的写法时（如 `ch` 单位、通用 `data-i18n` 属性），按工程约定修正实现，审美意图通过其他方式达成。

## 3. CJK 文字适配

### 3.1 问题本质

`ch` 单位定义为当前字体中数字 "0" 的宽度。在拉丁字母体系下，"0" 接近平均字符宽度，`ch` 是合理的文本容器宽度单位。但 CJK 字符是全角字符，宽度约为 "0" 的两倍，因此 `max-width: 18ch` 在中文环境下实际只能容纳约 9 个汉字，导致视觉上可以一行显示的标题被提前折断。

| 语言类型 | `ch` 含义 | 是否适合限制文本宽度 |
| --- | --- | --- |
| 拉丁字母（en 等） | 接近平均字符宽度 | 适合 |
| CJK 中文/日文/韩文 | 约为半个全角字符宽度 | 不适合，会低估约 50% |

### 3.2 单位选择规则

**触发条件**：目标页面文案包含 CJK 字符（中文、日文、韩文），或 `project.locale` / 文案主体为这些语言之一时。

CJK 场景下的单位替换表：

| 场景 | 禁用 | 推荐 | 原因 |
| --- | --- | --- | --- |
| 标题 `max-width` / `min-width` | `ch` | `em` / `rem` | 基于字号估算全角字符宽度更准确 |
| 文本截断容器宽度（`text-overflow: ellipsis`） | `ch` | `em` / 字符计数 JS | 同上 |
| 等宽布局容器 | `ch` | `rem` + 媒体查询 | 跨语言一致 |
| 段落阅读宽度限制 | `ch` | `%` / `em` | 相对容器或字号，语言无关 |

核心原则：**只要目标语言含 CJK 字符，就不使用 `ch` 单位限制文本宽度。**

### 3.3 中英文混排

- 测试纯 CJK 场景下的排版，不只在混排或纯拉丁下验证。
- 全角标点（。、，）和半角标点的混排间距在标题、按钮、卡片标题等短文本处影响最明显，应作为重点检查项。

## 4. 命名隔离与冲突防护

### 4.1 问题本质

通用属性名（如 `data-i18n`、`data-key`、`data-state`、`data-step`）是 i18next 等主流库的约定，本身没错。但运行环境（如浏览器预览工具、调试脚本、第三方注入）也可能扫描和操作这些通用属性，导致命名冲突——外部脚本在页面加载时覆盖或清除属性值，使页面自身逻辑失效。这类冲突在开发阶段难以预判。

### 4.2 属性命名规则

为页面自有的 `data-*` 属性添加项目前缀，降低与环境中其他脚本碰撞的概率：

| 通用名（高风险） | 带前缀（推荐） | 用途 |
| --- | --- | --- |
| `data-i18n` | `data-lp-t` | 翻译键 |
| `data-key` | `data-lp-key` | 通用数据键 |
| `data-step` | `data-lp-step` | 流程步骤标记 |
| `data-state` | `data-lp-state` | 元素状态标记 |
| `data-field` | `data-lp-field` | 字段绑定 |

前缀约定为 `lp-`（landing page）。业务规则中已显式要求保留的属性名（如 `data-verification-stage`）不在此替换范围内，按业务规则原样保留。

### 4.3 全局变量与作用域

- 所有页面 JS 包裹在 IIFE 或模块作用域内，不向 `window` 暴露实现细节。
- 必须暴露到全局的变量使用带前缀的命名空间（如 `window.LP = {...}`），避免与 `i18n`、`state`、`config` 等通用名冲突。
- 避免使用 `id` 选择器作为样式或脚本锚点，优先用带前缀的 class；必须用 ID 时加项目前缀（如 `lp-hero`）。

## 5. 运行环境兼容

### 5.1 注入脚本假设

生成的落地页可能运行在以下环境：

- 独立浏览器直接打开（最干净）；
- 带预览工具的编辑器内嵌 webview（可能有脚本注入）；
- 移动端内嵌 webview。

应假设页面运行环境存在外部脚本注入，按 4.2 和 4.3 的命名隔离规则避免冲突。不依赖"环境是干净的"这一假设。

### 5.2 初始加载正确性

页面首次加载时即应处于正确状态，不依赖用户首次交互来触发初始化：

- i18n 文案在 `DOMContentLoaded` 后立即应用，不等到首次语言切换；
- 默认值、初始视图、首屏可见元素在首次渲染时即正确；
- 避免在 `init()` 中依赖尚未就绪的外部资源。

### 5.3 字体加载

- 字体通过 Google Fonts CDN 或系统字体栈引入，不引用本地文件。
- 使用 `font-display: swap` 或回退字体栈，避免字体加载阻塞首屏文本渲染。
- CJK 字体回退栈应包含常见系统字体，确保无 CDN 时仍可阅读。

## 6. 工程自检清单

生成代码后，在交付前对照以下清单自检。这些项与 SKILL.md 第 7 步的业务和设计自检并列，只覆盖工程稳定性：

### CJK 适配（触发条件：目标语言含 CJK 字符）

- 所有 `max-width` / `min-width` / `width` 是否使用了 `ch` 单位？如是，替换为 `em` 或 `rem`。
- 文本截断（`text-overflow: ellipsis`）的容器宽度是否用 `ch`？如是，替换。
- 是否在纯中文场景下测试了标题、按钮、卡片标题的排版（不只在混排或纯拉丁下验证）？

### 命名隔离

- `data-*` 属性名是否使用了通用名（`data-i18n`、`data-key`、`data-state`）？如是，加 `lp-` 前缀。
- 业务规则要求保留的属性名（如 `data-verification-stage`）是否未被替换？
- 全局变量是否包裹在 IIFE 或命名空间内？暴露的全局变量是否带前缀？
- 是否有裸 `id` 选择器作为脚本或样式锚点？必须用 ID 时是否加了项目前缀？

### 运行环境兼容

- 是否假设了运行环境无外部脚本？如是，按命名隔离规则加固。
- 页面首次加载时 i18n 是否已正确应用（不仅是切换语言后）？
- 字体是否通过 CDN 或系统栈引入，无本地文件依赖？
- CJK 字体回退栈是否包含常见系统字体？

### 验证策略

除语法检查外，应在生成后执行浏览器冒烟测试，重点验证：

1. 初始状态正确性：页面加载后 i18n 文案、默认值、初始视图正确。
2. CJK 排版验证：截图检查标题、按钮、卡片标题是否存在非预期换行。
3. 控制台零错误：检查是否有 JS 运行时错误或属性被外部脚本干扰的迹象。

这类测试能捕获语法检查无法发现的环境冲突问题。

## 7. 适用边界

- 本文档规则是**条件性**的：CJK 规则只在目标语言含 CJK 字符时触发，命名隔离规则在运行环境可能有注入脚本时相关。AI 应根据实际配置判断哪些规则适用，而非把所有规则当无条件硬规则套用。
- 当配置明确指定目标语言为拉丁字母体系、且运行环境确认为干净浏览器时，CJK 单位规则可不触发，但命名隔离规则仍建议执行（成本极低，收益为规避难以预判的冲突）。
- 本文档不定义业务正确性。业务行为是否符合配置，由 `business-rules.md` 和配置事实约束。
